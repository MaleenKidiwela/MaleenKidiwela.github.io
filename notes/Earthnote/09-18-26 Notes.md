
## QA/QC dashboard information

The qaqc.ooi-rca.net site is a precomputed visualization layer, not a direct OOINet/M2M client. Its browser-facing data paths map almost 1:1 onto objects in an AWS S3 bucket:

`OOI/Zarr inputs → plotting pipelines → s3://ooi-rca-qaqc-prod → Nuxt proxy → browser`

### Confirmed data paths

|Data|Public site path|Backing S3 object|
|---|---|---|
|Plot manifest|`/QAQC_plots/index.json`|`s3://ooi-rca-qaqc-prod/QAQC_plots/index.json`|
|Plot images|`/QAQC_plots/<site>/<filename>.png` or `.svg`|Same key beneath `QAQC_plots/`|
|HITL manifest|`/HITL_notes/index.json`|`s3://ooi-rca-qaqc-prod/HITL_notes/index.json`|
|HITL tables|`/HITL_notes/<table>.csv`|Same key beneath `HITL_notes/`|
|Discrete summaries|`/discrete/summary-samples.csv`|`s3://ooi-rca-qaqc-prod/discrete/summary-samples.csv`|
|CTD cast samples|`/discrete/ctd-cast-samples.csv`|`s3://ooi-rca-qaqc-prod/discrete/ctd-cast-samples.csv`|
|Hydrophone images|`/spectrograms/<YYYY>/<sensor>/<sensor>_<YYYYMMDD>.png`|Same key beneath `spectrograms/`|
|Echosounder images|`/echograms/<YYYY>/<sensor>/<sensor>_<YYYYMMDD>.png`|Same key beneath `echograms/`|
|Archived plots|`/archives/<type>/<key>/QAQC_plots/...`|Same key beneath `archives/`|
|Archive metadata|`/api/archives`|SQLite archive records|

The middleware explicitly recognizes those six S3 prefixes and passes the request path directly to AWS `GetObject`; only `archives/internal/` requires login. [Proxy prefix source](https://github.com/OOI-CabledArray/QAQC_dashboard/blob/d8fa9e30ff5459f51f4e431cf2aa9e20f3985c96/dashboard/server/middleware/02.s3-proxy.ts#L1-L25), [S3 request mapping](https://github.com/OOI-CabledArray/QAQC_dashboard/blob/d8fa9e30ff5459f51f4e431cf2aa9e20f3985c96/dashboard/server/utils/s3-proxy.ts#L5-L45).

Live checks today showed:

- [`/QAQC_plots/index.json`](https://qaqc.ooi-rca.net/QAQC_plots/index.json): 83,390 plot objects across 14 sites.
- [`/HITL_notes/index.json`](https://qaqc.ooi-rca.net/HITL_notes/index.json): 61 CSV tables.
- Both discrete CSVs and sampled plot, spectrogram, and echogram paths returned HTTP 200.
- Responses carry `ETag`, `Last-Modified`, and `Cache-Control: public, max-age=15`.

The frontend first downloads the plot manifest, filters its relative keys, and constructs URLs under `/QAQC_plots/`. [Frontend loading logic](https://github.com/OOI-CabledArray/QAQC_dashboard/blob/d8fa9e30ff5459f51f4e431cf2aa9e20f3985c96/dashboard/app/store.ts#L339-L401).

### Upstream sources

The main scientific plot pipeline reads:

- Zarr stores at `s3://ooi-data/<zarrFile>`, where `<zarrFile>` comes from `sitesDictionary.csv`.
- Annotations at `s3://ooi-data/annotations/<reference-designator>.json`.
- Example Zarr path:  
    `s3://ooi-data/CE02SHBP-LJ01D-06-CTDBPN106-streamed-ctdbp_no_sample`

It opens these using `xarray.open_zarr(..., consolidated=True)`, generates plots, and uploads them under `QAQC_plots/<site>/...`. [Plot input code](https://github.com/OOI-CabledArray/rca-data-tools/blob/03358ff29267dfa7ecede48c28915adb58ecb6ce/rca_data_tools/qaqc/dashboard.py#L43-L61), [Zarr loader](https://github.com/OOI-CabledArray/rca-data-tools/blob/03358ff29267dfa7ecede48c28915adb58ecb6ce/rca_data_tools/qaqc/dashboard.py#L306-L314).

Other inputs include:

- Discrete samples: `https://rawdata-west.oceanobservatories.org/files/cruise_data/Cabled/*/Water_Sampling/...`
- HITL status: a Google Sheet named `HITL Data QA/QC Log`, converted to CSV and synchronized to S3.
- Deployment history: `raw.githubusercontent.com/oceanobservatories/asset-management/.../<site>_Deploy.csv`
- Profiler indices: `raw.githubusercontent.com/OOI-CabledArray/profileIndices/...`
- Operational status: `https://nereus.ooirsn.uw.edu/api/public/v1/instruments/operational-status`
- Event Report configuration: three CSV files loaded directly from the `rca-data-tools` GitHub repository.

For an agent, I would treat `/QAQC_plots/index.json` as the canonical plot catalog and use conditional requests with its ETag. The bucket itself does not need to be exposed to the agent. Also, `backups/database/...` is documented in the bucket but is not part of the public proxy whitelist. [Architecture and bucket structure](https://github.com/OOI-CabledArray/QAQC_dashboard/blob/d8fa9e30ff5459f51f4e431cf2aa9e20f3985c96/dashboard/README.md#L184-L240).

### What can run locally

|Component|Available?|Local requirements|
|---|--:|---|
|Nuxt dashboard|Yes|Node.js 24|
|Users, sessions, archives|Yes|Local SQLite|
|Standard QA/QC plot generation|Yes, in `rca-data-tools`|Python environment plus source Zarr access|
|Plot indexing|Yes|Local filesystem or object store|
|Discrete CTD/sample processing|Yes|Downloads from OOI’s public raw archive|
|Deployment/profile metadata|Yes|Public GitHub sources|
|Nereus operational status|Yes|Public API|
|HITL note generation|Partly|Access to their private Google Sheet, or replace it|
|Hydrophone/seismometer/echogram processing|Partly|Public container images exist, but data access and some pipeline code/configuration may be external|
|Creation of the upstream `ooi-data` Zarr stores|Not in these repos|We need our own OOI ingestion/Zarr-building pipeline|

### Recommended local architecture

```text
Official OOI data
      ↓
Our ingestion and Zarr store
      ↓
rca-data-tools plot generation
      ↓
Our local object store
      ↓
Local QA/QC dashboard
      ↓
Our agent tools and GraphRAG
```

I would make the following changes:

1. Replace the hard-coded `ooi-data/` input bucket with something configurable, such as:
    ```text
    QAQC_INPUT_STORE=/data/ooi-zarr
    QAQC_OUTPUT_STORE=/data/qaqc
    ```
2. Replace the production S3 dependency with either:
    - A filesystem backend for one machine, or
    - MinIO if we want a locally hosted S3-compatible interface.

3. Run `rca-data-tools` directly rather than through their Prefect Cloud workspace.
4. Replace GitHub Actions schedules with cron or a local workflow scheduler.
5. Generate our own:
```text
    QAQC_plots/index.json
    HITL_notes/index.json
```
3. Have the dashboard and agent query the same local artifact catalog.
### What we still need to obtain

The largest missing piece is the dataset behind:

```text
s3://ooi-data/<reference-designator>-<delivery-method>-<stream>
```

The plotting code expects consolidated Zarr datasets at those paths. We have three options:

- Obtain authorized access to the existing `ooi-data` bucket.
- Ingest official OOI data ourselves and convert it to the expected Zarr layout.
- Modify `rca-data-tools` to work with our chosen canonical dataset format.

For your system, the second option gives us the most control and provenance.

The private HITL Google Sheet is another unavailable input. We should replace it with our own structured annotation/QC table rather than depend on their legacy sheet workflow.

### Practical migration path

We do not need to reproduce everything before starting:

1. Mirror the currently public manifests, plots, discrete CSVs, spectrograms, echograms, and public archives to our machine.
2. Run the cloned dashboard against that local snapshot.
3. Build our own OOI-to-Zarr ingestion path.
4. Turn on local plot regeneration instrument by instrument.
5. Replace the mirrored artifacts as our pipeline produces them.

For the agent, this is better than depending on the public site: we control refresh timing, provenance, temporal intervals, data-quality validation, and scientific calculations. The dashboard then becomes one interface over our local data platform rather than an external source we must scrape.

**we can own the complete serving, retrieval, QA/QC, plotting, archive, and agent layers locally**. The part we must build or obtain separately is the upstream observation-data ingestion that creates the Zarr stores.
