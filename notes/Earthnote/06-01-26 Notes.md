# 06-01-26 — Implementing "Predicting New Research Directions" in Our Notes App

## Paper Summary

**Paper:** Marwitz et al. (2026), *Predicting new research directions in materials science using large language models and concept graphs*. Nature Machine Intelligence 8, 535-544.

**Core pipeline (their version):**

1. **Concept extraction** -- Fine-tuned LLaMA-2-13B extracts key concepts from ~221K materials science abstracts. Superior to RAKE (rule-based keyword extraction) because the LLM can nominalize, remove filler words, normalize plurals, and extract concepts not verbatim in the text.
2. **Concept graph** -- Nodes = concepts (filtered: ≥3 occurrences, ≥2 words). Edges = co-occurrence in the same abstract. The graph is *temporal*: each edge carries the publication date. Result: ~137K nodes, ~13M edges.
3. **Concept embeddings** -- MatSciBERT encodes each concept in-context (averaged across all abstract occurrences) to produce 768-dim semantic vectors per concept node.
4. **Link prediction** -- Binary classification: will two currently-unconnected concepts co-occur in a future paper? Four model variants:
   - *Baseline*: Graph topology features only (node degree + 2-path count at 5 historical time slices → 20-dim feature vector per node pair)
   - *Concept embeddings only*: Concatenated 768-dim vectors per pair (1,536-dim)
   - *Combination of features*: Concatenate both (1,556-dim)
   - *Combination of models*: Weighted average of independent model outputs (best: 60/40 baseline/embeddings, AUC 0.9372)
5. **Report generation** -- For a specific researcher, compute their "own concepts" (C_own) from their publications, then rank predicted links involving C_own. Filter by heuristics (avoid generic concepts, avoid too-similar or too-unrelated pairs via embedding distance). An LLM curates the top suggestions with explanatory paragraphs.
6. **Expert interviews** -- 10 materials scientists evaluated the suggestions. 29% rated "interesting/inspiring" (51% precision when LLM pre-curated).

**Key insight for us:** The paper's power is in the temporal concept graph + link prediction. Concepts that haven't co-occurred yet but are predicted to form links represent potential new research directions. The semantic embeddings improve prediction especially at distance dprev=3, i.e., the more surprising, non-obvious connections.

### Scale difference

Their system: ~221K abstracts, ~137K concept nodes, ~13M edges.
Our system: ~40 markdown notes, ~1,054 concepts, ~236 chunks.

This is a *personal knowledge base*, not a public literature corpus. The approach adapts: instead of predicting what *the field* will do next, we're predicting what *Maleen* should investigate next -- connections between concepts across projects and notes that haven't been explored together yet.

## Implementation Plan

### Phase 1: Build the Temporal Concept Co-occurrence Graph

**Goal:** Transform the existing flat concept index into an explicit, temporal, weighted graph.

**What changes in `index-notes.mjs`:**

Add a new output artifact: `concept-graph.json` containing:

```json
{
  "generatedAt": "...",
  "nodes": [
    {
      "id": "methods:cross-correlation",
      "label": "cross-correlation",
      "kind": "method",
      "degree": 47,
      "firstSeen": "2026-04-09",
      "lastSeen": "2026-05-29",
      "projects": ["COSZO", "BransfieldEQ", "Earthnote"],
      "chunkCount": 6,
      "noteCount": 5
    }
  ],
  "edges": [
    {
      "source": "methods:cross-correlation",
      "target": "quantities:dv/v",
      "weight": 3,
      "dates": ["2026-04-28", "2026-04-29", "2026-05-29"],
      "projects": ["Earthnote"],
      "chunks": [179, 180, 232]
    }
  ],
  "stats": { "nodeCount": 1054, "edgeCount": "...", "density": "..." }
}
```

**How edges are defined (adapting the paper):**

In the paper, two concepts co-occur if they appear in the *same abstract*. For us, the analogous unit is the *same chunk* (since a note can cover multiple topics in different sections). Two concepts share an edge if they were both extracted from the same chunk. The edge weight = number of chunks where they co-occur. Each edge carries the dates from the chunks' `dateFromFilename`.

**Implementation detail:**

```
for each chunk c:
  concepts_in_c = byChunk[c.id]
  for each pair (a, b) in concepts_in_c where a.id < b.id:
    add or increment edge(a, b)
    record c.dateFromFilename on edge
```

This is O(C^2) per chunk where C is concepts per chunk, but C is typically 3-8, so it's cheap.

### Phase 2: Compute Concept-Level Embeddings

**Goal:** Each concept node gets a 768-dim semantic embedding, derived from the chunk-level Gemini embeddings.

**Approach (following the paper's MatSciBERT method, adapted):**

For each concept, collect all chunks where it appears. Average the chunk embeddings to get the concept embedding. This is a reasonable approximation since each chunk embedding already captures the semantic context of its concepts.

```javascript
const conceptEmbeddings = {};
for (const concept of concepts) {
  const vecs = concept.chunkIds.map(id => embeddingSlice(id));
  conceptEmbeddings[concept.id] = averageVectors(vecs);
}
```

**Output:** `concept-embeddings.bin` -- Float32Array, same format as `embeddings.bin` but indexed by concept node order.

**Alternative (higher quality but more API calls):** Embed each concept label directly via `RETRIEVAL_DOCUMENT` with context like:
`"marine geophysics :: {concept.kind} :: {concept.display} :: [appears in: {noteIds}]"`

This would be more faithful to the paper's approach (they embed the concept in the context of each abstract). For our scale (~1,054 concepts), this is ~42 embed API calls at batch size 25. Totally feasible. **I recommend this approach.**

### Phase 3: Link Prediction -- Finding Missing Connections

**Goal:** Score all *non-existing* concept pairs and rank them by likelihood of being a productive research connection.

**The paper's approach** uses a neural network trained on historical data. We don't have enough historical data for that (40 notes vs. 221K abstracts). We need a simpler scoring function.

**Proposed scoring function (adapted for small corpus):**

For a pair of currently-unconnected concepts (u, v):

```
score(u, v) = α * semantic_similarity(u, v)
            + β * shared_neighbor_score(u, v)
            + γ * cross_project_bonus(u, v)
            + δ * temporal_recency(u, v)
```

Where:
- **semantic_similarity(u, v)** = cosine similarity of concept embeddings. High similarity suggests related ideas that haven't been combined yet.
- **shared_neighbor_score(u, v)** = Jaccard index of their graph neighborhoods (analogous to the paper's "common neighbors" / 2-path features). Concepts that share many neighbors but aren't directly connected are strong candidates.
- **cross_project_bonus(u, v)** = bonus when u and v come from *different* projects. Cross-pollination between COSZO, BransfieldEQ, and Earthnote is exactly the kind of "novel combination" the paper targets.
- **temporal_recency(u, v)** = concepts appearing in recent notes are more likely to be actively relevant.

**Filtering heuristics (from the paper):**
- Exclude pairs where both concepts are very generic (high degree, like "histogram" or "sampling rate").
- Exclude pairs where semantic similarity is too high (>0.95 -- they're basically synonyms) or too low (<0.3 -- no plausible connection).
- The paper calls this the "Goldilocks zone" for novelty.

**Output:** A ranked list of concept pairs with scores, stored as `predictions.json`:

```json
{
  "generatedAt": "...",
  "predictions": [
    {
      "source": { "id": "methods:beamforming", "display": "beamforming", "kind": "method", "projects": ["BransfieldEQ"] },
      "target": { "id": "quantities:dv/v", "display": "dv/v", "kind": "quantity", "projects": ["Earthnote"] },
      "score": 0.847,
      "semanticSim": 0.61,
      "sharedNeighbors": 3,
      "crossProject": true,
      "rationale": null
    }
  ]
}
```

### Phase 4: LLM-Generated Research Direction Rationales

**Goal:** For the top-N predicted links, use Gemini to generate a paragraph explaining *why* these concepts could be productively combined, following the paper's "LLM Curation" step.

**Prompt template:**

```
You are a research advisor for a marine geophysicist.

Two concepts from different research projects have been identified as a
potentially productive but unexplored connection:

Concept A: "{display_a}" ({kind_a})
  - Appears in: {projects_a}
  - Context: {sample_chunk_text_a}

Concept B: "{display_b}" ({kind_b})
  - Appears in: {projects_b}
  - Context: {sample_chunk_text_b}

These concepts share {shared_neighbors} neighbors in the concept graph
but have never appeared together in the same note.

Write 2-3 sentences explaining:
1. Why combining these concepts could lead to a new research direction
2. What specific experiment, analysis, or investigation this combination suggests
3. How this could build on existing work in both projects
```

**This runs at build time** (during `npm run index`) and the rationales are baked into `predictions.json`. Cost: ~20 Gemini 2.5 Flash calls for top-20 predictions. Cheap.

### Phase 5: UI -- The "Research Directions" Tab

**Goal:** Add a new tab (or section within the existing Concepts tab) that surfaces the predicted research directions.

**Design:**

Two possible approaches:

**Option A: "Suggestions" panel in the Concepts tab**
- Bottom drawer or side panel in the existing constellation view
- When you click a concept node, the panel shows "Unexplored connections" -- concept pairs involving that node, ranked by prediction score
- Each suggestion shows the LLM-generated rationale

**Option B: Dedicated "Directions" tab alongside Dashboard/COSZO/BransfieldEQ/Earthnote**
- Card-based layout showing top-20 predicted research directions
- Each card shows the two concepts, their projects (color-coded), the score, and the LLM rationale
- Filterable by project, kind, or score threshold
- Clicking a card highlights the relevant nodes and path in the constellation graph

**I lean toward Option A** because it integrates naturally with the existing concept graph visualization. The constellation already has the nodes and edges. Predicted links could be rendered as *dashed lines* in a different color (e.g., the accent color with lower opacity) overlaid on the existing graph.

### Phase 6: RAG Integration -- "What Should I Work On?"

**Goal:** Make the predictions queryable through the chat.

**Changes to `chat.js`:**
- Load `predictions.json` alongside the other assets
- Detect intent queries like "what should I work on next?", "suggest research directions", "what connections am I missing?"
- Instead of doing normal RAG retrieval, inject the top predictions + rationales as context
- The system prompt gains a new mode: "The user is asking for research direction suggestions. Use the following predicted concept connections..."

**Changes to the worker (optional):**
- A new endpoint `POST /suggest` that takes C_own (user's active project concepts) and returns filtered predictions
- Or keep it all client-side since the predictions are precomputed

## Open Questions

1. **Concept granularity:** Should we merge related concepts (e.g., "cross-correlation" and "ambient noise cross-correlation") before building the graph? The paper applies ≥3 occurrences + ≥2 words filter. We should apply something similar but our corpus is smaller.

2. **Chunk vs. note level:** Should co-occurrence be defined at the chunk level (finer grained, more edges) or note level (coarser, fewer edges)? The paper uses abstract-level. Our chunks are similar in size to abstracts (~200-500 words). I say chunk level.

3. **Minimum concept frequency:** The paper requires ≥3 occurrences. With only ~236 chunks, should we lower this to ≥2? Or keep singletons for the graph but exclude them from predictions?

4. **When to recompute:** Predictions should refresh whenever `npm run index` runs (triggered by GitHub Action on push to notes). This keeps predictions in sync with the vault.

5. **How many predictions to surface:** The paper generates ~30-50 per researcher. For us, top-20 might be enough. Possibly filterable by project focus.
