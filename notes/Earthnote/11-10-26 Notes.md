## 3. Literature Evaluation & Abstention Protocols

Evaluating model performance on scientific literature presents unique challenges compared to standard coding tasks. While coding tasks rely on deterministic execution and syntax verification, literature analysis requires evaluating how models handle incomplete, ambiguous, or impossible queries.

A core objective of the literature evaluation framework is measuring model abstention—the capability of an agent to explicitly state "I don't know" or "I don't have the information" when a query cannot be answered. Abstention is formally treated as a valid, high-quality response rather than an evaluation failure.

The literature benchmark explicitly incorporates two challenging query categories:

- **Unanswerable Questions**: Scientific queries where the current body of literature contains no established answer or evidence.
- **False Concept Questions**: Queries containing invalid premises, false assumptions, or non-existent concepts.

Ensuring the model refrains from hallucinating plausible-sounding answers when encountering impossible or false queries is essential for establishing research-grade AI reliability.

## 4. Human-in-the-Loop Evaluation Architecture (Google Sheets)

To facilitate efficient human review without requiring evaluators to interact directly with raw JSON files, the team designed a standardized Google Sheets review queue. This queue provides an accessible interface for domain experts to validate model outputs.

The review sheet is structured to streamline the human reviewer's workflow while preserving data integrity. Each row corresponds to a single Question-Answer (QA) pair, organized into functional columns:

- **Question Column (****Q****)**: The input prompt or evaluation query being tested.
- **Evidence Column**: The supporting scientific literature or reference paper used to verify the answer.
- **AI Generated Answer Column**: The model-generated output, which can be optionally hidden from reviewers to avoid confirmation bias.
- **Human Reviewer Answer Column**: The verified evaluation score or corrective answer provided by the domain expert.
- **Abstention & Standardized Response Dropdown**: A pre-configured dropdown menu with fixed options (such as _"I do not know"_ or _"I don't have the information"_).

To optimize the evaluation process, specific operational features were established for the spreadsheet interface:

- **Blinded & Unblinded Review**: Hiding AI-generated answers prevents evaluators from being prematurely influenced by candidate model outputs.
- **Standardized Dropdown Menus**: Derived from a prior project on encoding abstracts for Data/AI readiness, pre-configured dropdowns accelerate reviewer decision-making when selecting standard outcomes.
- **Distributed Workload Allocation**: Review tasks will be offloaded across team members, such as assigning 50-item evaluation batches to Michael and March.
- **Golden Dataset Serialization**: Once human evaluations are completed, the spreadsheet data will serve as the master golden dataset, which will be exported back into JSON format for integration with automated evaluation frameworks.

## 5. Model Robustness, Typo Sensitivity, & Benchmark Metrics

During preliminary testing with Gemma, significant sensitivity to prompt phrasing and minor typographical errors was observed. Minor typos or slight phrasing variations caused the model to fail to retrieve or recognize correct information, resulting in immediate performance degradation.

This vulnerability highlighted the necessity of measuring **Model Robustness** as an explicit benchmark metric across all candidate base models, rather than relying solely on prompt engineering fixes.

|   |   |   |
|---|---|---|
|Robustness Dimension|Context & Impact|Lesson / Strategy|
|**Typo Tolerance**|Gemma fails or claims ignorance when input contains minor typos.|Robustness must be evaluated across different base models to separate model limits from prompt issues.|
|**Prompt Sensitivity**|Slight changes in word choice lead to inconsistent retrieval performance.|Over-optimizing prompts creates brittle systems; base model selection must prioritize inherent robustness.|
|**Non-Native Author Text**|Prior consulting work with ~200 expert scientists revealed heavy iteration needs due to non-native writing.|Real-world scientific literature contains diverse phrasing; models must handle natural linguistic variations.|

Evaluating how different base models handle linguistic variations ensures that system performance remains reliable across diverse real-world user populations.

## 6. Base Model Comparison & Local Model Retraining

The evaluation strategy emphasizes testing multiple base model architectures rather than relying on a single model family. Gemma currently serves as the baseline test case due to its speed and deployment convenience as a local LLM dedicated to a single user.

To establish comprehensive benchmarks, the team will expand evaluations to alternative architectures and investigate model retraining techniques:

- **Alternative Model Evaluation**: Incorporate models such as (OLMO) into the comparison pipeline to benchmark performance differences against Gemma.
- **Weight Modification Experiments**: Investigate retraining small local models by directly modifying model weights. Because smaller models possess fewer weights, they can be modified and executed locally on standard hardware.
- **Focus Area (RAG & Encoding)**: Retraining efforts will focus strictly on Retrieval-Augmented Generation (RAG) and document encoding workflows. Out-of-scope capabilities, such as image generation, will be excluded.
- **Collaboration with Brad**: Brad has been actively experimenting with weight modification techniques for small models; the team will consult Brad to refine local retraining protocols for RAG workflows.

## 7. Knowledge Retrieval vs. Web Access Trade-Offs

The team evaluated the architectural trade-offs between models equipped with live web search capabilities and models operating strictly on baked-in knowledge or local recipes.

While high-tier models with web search access can dynamically pull the latest external resources (such as recent GitHub repositories), local models without web access provide critical operational advantages:

- **Sandboxing & Security**: Disabling web search access ensures strict sandboxing, preventing external data leakage and eliminating risks associated with uncontained agent execution.
- **Controlled Evaluation**: Local models (like Gemma) operate in an isolated environment, ensuring that evaluation results are fully reproducible and uninfluenced by changing external web content.
