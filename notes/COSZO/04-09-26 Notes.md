## Mode 1: `collect` — Build the Metrics Library

### What it does

Loops over every (station, date) combination in the requested range. For each:

1. Determines the correct deployment number from the date (using param file date ranges)
2. Fetches NetCDF timestamps from the OOI M2M API (same fetch logic as now)
3. Handles no-data gracefully (logs a `NO_DATA` row, moves on)
4. Runs `compute_stats()` (already exists)
5. Computes **William's jitter metric** (see below)
6. Appends one row to the station's metrics CSV
7. If anomaly triggers are met, generates a per-day figure (existing `make_figure`)

### Per-day figure layout (revised)

Replace the current Panel 1 (sample index vs timestamp) with a **histogram of timing residuals**. The timestamp-vs-index plot is useful for understanding overall shape but redundant once you have the Δt panel — the histogram gives the distributional information that's actually hard to read from the scatter.

**New 3-panel layout:**

| Panel | Content | What it shows |
|-------|---------|---------------|
| 1 | **Histogram of residuals** (ms, from best-fit line) | Shape of jitter distribution: Gaussian = random noise, bimodal = quantization artifact, long tail = occasional large timing errors |
| 2 | Residuals scatter (sample index vs residual in ms) | Temporal structure — drift over the day, clusters, sudden jumps |
| 3 | Δt between consecutive samples with adaptive gap threshold | Gap detection, whether threshold is well-placed |

Histogram details:
- X axis: residual in ms, centred at 0
- Bin width: auto (Freedman-Diaconis or fixed ~1ms bins)
- Vertical lines: ±1σ, ±p95
- Annotate: σ, p95, skewness, n samples
- Overlay a Gaussian curve fit for easy comparison

The residuals scatter (Panel 2) stays because it shows *when* during the day the jitter occurs — the histogram alone loses that temporal information.

**`compute_stats()` must be refactored to follow this order:**

**Step 1 — Gap detection**
- Compute all Δt (`np.diff(t_sec)`) across the full day
- Estimate day-level `sp_calc` from the full Δt array (robust median of lower 90th percentile — resistant to large gap intervals so this still works)
- Apply adaptive threshold, identify `gap_idx`
- Log: `n_gaps`, gap locations, gap durations, estimated missing samples per gap

**Step 2 — Per-segment sample rates**
- Split `t_sec` into contiguous segments at `gap_idx`
- For each segment: compute its own `sp_calc_seg` (robust median Δt within that segment)
- Log: segment index, duration, sample count, sample rate
- Detects whether segments disagree — e.g. sensor slowed down after a dropout

**Step 3 — Jitter metrics (per segment, then concatenated)**
- For each segment independently: fit a line, compute residuals
- Compute William's metric using the **segment-level** `sp_calc_seg` as the denominator:
  `jitter_i = |dti / sp_calc_seg - round(dti / sp_calc_seg)|`
- Using segment-level rate matters: if two segments run at slightly different rates, measuring jitter against a blended day-level average fits neither segment correctly
- Concatenate residuals and jitter values across all segments
- Compute summary stats of the combined jitter array:
  - `jitter_mean` — mean
  - `jitter_median` — median (robust central tendency)
  - `jitter_std` — standard deviation
  - `jitter_p95` — 95th percentile (anomaly trigger candidate)
  - `jitter_max` — maximum (catches worst single interval)
- Compute summary stats of the combined residuals array:
  - `res_std_ms` — standard deviation in ms
  - `res_p95_ms` — 95th percentile in ms
  - `skewness` — asymmetry (negative/positive drift within segments)

**Important: residuals must be computed per segment, not across the whole day.**

If there is a gap mid-day and the best-fit line is fitted through all samples across the gap, the line slope is distorted by the gap. Samples before the gap appear systematically early and samples after appear systematically late — the histogram shows a smeared or bimodal distribution that looks like jitter or drift but is purely a gap artifact.

Correct approach:
1. Detect gaps first (`gap_idx` already available)
2. Split `t_sec` into contiguous segments at gap boundaries
3. For each segment independently: fit a line, compute residuals
4. Concatenate all segment residuals into one array
5. Histogram and scatter are built from this concatenated array

This ensures residuals reflect only within-segment timing irregularity.

For the residuals scatter (Panel 2): colour-code points by segment so it is visually clear which residuals belong to which contiguous block. Gaps appear as breaks between colour groups.

### Anomaly triggers (generate per-day figure)

For the **first pass**, only trigger on structural anomalies where no baseline is needed:
- Any gap detected (`n_gaps > 0`)
- Day is incomplete (`is_full = False`)
- Sample period deviation exceeds hybrid alert threshold (`sp_alert = True`)

**Jitter threshold is disabled on the first pass.** The current code computes `res_std`, `res_p95`, and William's jitter metric per day, but there is no meaningful threshold to compare against yet — every sensor has some baseline spread from network ingestion delays and timestamp rounding, and `res_std > 0` is always true.

To establish a jitter threshold:
1. Run `collect` over a 30–60 day test window
2. Plot jitter p95 over time (summary Figure 3)
3. The distribution of values across clean days defines the normal baseline
4. Flag days where jitter p95 exceeds e.g. 3× the median baseline as anomalous
5. Set that value as `jitter_p95_threshold` in `run_prest.txt` and enable the trigger

Until Step 4 is done, jitter-based figure triggering is a guess. All jitter metrics are still **stored in the CSV** every day regardless — the threshold only controls whether a figure is generated.

### Skip logic

If a row for this (station, date) already exists in the CSV, skip the API fetch — this lets the script be re-run incrementally without re-fetching data.

## William's Jitter Metric

Defined as:
```
jitter_i = |dti / mean_dt - round(dti / mean_dt)|
```

Where:
- `dti` = inter-sample intervals (`np.diff(t_sec)`)
- `mean_dt` = `sp_calc` (robust median sample period, same as the pipeline uses)

**Interpretation:**
- For a perfectly uniform signal: `dti / mean_dt ≈ 1.0` for every interval → jitter ≈ 0
- For a jittered signal: each interval deviates slightly from an integer multiple → jitter > 0
- For a genuine gap: `dti / mean_dt` is a large integer (e.g. 5, 10, …) → `round()` cancels it → jitter ≈ 0 again
- The metric is **insensitive to gaps** and specifically sensitive to sub-sample timing irregularity

Per-day summary statistics stored: `jitter_mean`, `jitter_p95`, `jitter_max`

Note: William also suggested using the nominal sample rate instead of `mean_dt` as an alternative. We will compute both and compare during the first test run.

## API Call Timing

**Pressure channel only.** `fetch_nc_timestamps` reads only the `time` variable from the NetCDF — never pressure or temperature values. Temperature timestamps are identical to pressure. One API call per station per day is sufficient. No code change needed.

**Why calls are slow.** The OOI M2M API is async:
1. Submit request (~instant)
2. Poll `status.json` until job completes (`max_cycle=5`, `delay=50s` → up to 250s wait)
3. Open NetCDF via OPeNDAP and read timestamps

In practice a 24h window completes in 1–2 polls ≈ 50–100s per call.

**Scale estimate.** 3 stations × ~4000 days = ~12,000 calls × ~90s = ~12 days wall clock. Collect must run in chunks across multiple sessions. The CSV skip logic handles this — already-processed rows are skipped on resume.

**First step: time one call.**
```bash
cd coszo-data-collection
source .ooi_env
time conda run -n ooi_env python bin/diagnose_timing.py \
    --mode single \
    --station RS01SLBS-MJ01A-06-PRESTA101 \
    --date 2025-01-01
```
Result tells us actual per-call timing and whether the diagnostic output looks correct before committing to a longer run.
