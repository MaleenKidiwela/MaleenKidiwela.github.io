## What is Graph RAG and how is it made?

Graph RAG adds a structured layer between the corpus and the LLM.

At indexing time an LLM (Named Entity Recognition (NER) and Relationship Extraction) reads the documents and pulls out entities (people, instruments, sites, methods) and the relations between them, which together form a knowledge graph. But this would be for raw unstructured text. The LLM identifies nodes (e.g., `Company`, `Person`) and edges (e.g., `WORKS_FOR`, `SUPPLIES`).

But our corpus is a bit more structured.

## Deterministic entity and relationship extraction

We used rules and source structure instead of asking a model to infer meaning.

For structured OOI/COSZO records — instruments, sites, channels, papers, figures, tools, etc.:

| JSON field | Becomes |
|---|---|
| `instrument_id` | Instrument node |
| `site` / `site_id` | Site node |
| `channel_id` / `parameter` | Channel or Parameter node |
| Known source fields together | Relationship |

Example:

```json
{
  "instrument_id": "INSTRUMENT-...",
  "canonical_id": "PI-A0ABPA301",
  "physical_site": "Central Caldera, Axial Seamount",
  "site_id": "ENTITY-d9e65f2c5695608",
  "endpoint_ids": ["PI-PORTAL-ENDPOINT-..."]
}
```

## How RCA Atlas's graph is actually built

RCA Atlas's production graph is not built with Microsoft GraphRAG. It is built from scratch like this:

```text
Source-specific pipelines
  → normalized JSONL records
  → stable IDs for chunks, instruments, sites, channels, papers, figures, tools
  → explicit provenance-backed relationships
  → checksum manifest validation
  → PostgreSQL graph nodes + edge facts
  → pgvector embeddings for chunks
```

Examples of existing explicit edges:

- Instrument → deployed at → site
- Instrument → measures → parameter/channel
- Paper → has chunk → abstract passage
- Chunk → source → publication/web page
- Tool → retrieves → data system

Then, at question time:

```text
keyword + vector retrieval
  → initial chunks/entities
  → graph-neighbor traversal
  → reranking
  → cited evidence package
  → answer or appropriate live tool
```

> [!note] Why not Microsoft GraphRAG
> Microsoft GraphRAG works differently: it uses an LLM to infer entities/relationships from unstructured text and can create community summaries. We prepared it as a separate candidate extractor, but did not make it the production graph because RCA Atlas already has structured OOI/COSZO identifiers and needs strict provenance. It can strengthen the full-text layer later, after we configure an extraction model and evaluate its inferred edges against this deterministic baseline.

## Source-specific pipelines

"Source-specific pipelines" means we wrote different parsers for each kind of source, because an OOI instrument catalog, a paper bibliography, an Axial earthquake feed, and a PDF figure do not have the same structure.

For example:

**OOI / PI portal catalog**

```text
→ parse instrument IDs, aliases, sites, nodes, endpoints, channels
→ create Instrument, Site, Channel, Data-access nodes
→ create explicit edges:
   Instrument → DEPLOYED_AT → Site
   Instrument → HAS_CHANNEL → Channel
   Instrument → AVAILABLE_FROM → PI portal / OOI system
```

**Literature catalog**

```text
→ parse DOI, title, authors, abstract, citation records
→ create Paper and Abstract-chunk nodes
→ create explicit edges:
   Paper → AUTHORED_BY → Author
   Paper → HAS_CHUNK → Abstract chunk
   Paper → ABOUT → curated topic/site
```

**Website / datasheet / figure pipelines**

```text
→ extract page, section, figure, caption, source URL
→ create Page, Figure, Datasheet nodes
→ create explicit source and parent-child edges
```

**Axial / EarthScope / Nereus / QA-QC pipelines**

```text
→ parse their structured records and tool metadata
→ create event, station, tool, data-source, QA-rule nodes
→ create explicit relationships from the source fields
```

### Assembly

The builders write standard JSONL files:

```text
instruments.jsonl
sites.jsonl
channels.jsonl
documents.jsonl
chunks.jsonl
entities.jsonl
relationships.jsonl
tools.jsonl
```

Then `src/graphrag_runtime/normalize_corpus.py` does the generic assembly step:

```text
all pipeline JSONL
→ verify file SHA-256 and record counts against manifest
→ validate every edge endpoint exists
→ turn records into graph nodes, chunks, identifiers, and edge facts
→ load them into PostgreSQL / pgvector
```

RCA Atlas is primarily Pattern 4: Sequential Hybrid, Vector-First.

  Its current flow is:

  Question
  → semantic vector retrieval + keyword retrieval
  → RRF fusion
  → initial chunks and their graph entities
  → graph-neighbor expansion
  → reranking
  → cited evidence package
  → answer model

  So it starts with text retrieval, then uses the graph to add connected instruments, sites, channels, publications, figures, and tools.


It is not currently:

  - Pattern 1, Text-to-Cypher — Atlas does not ask an LLM to generate arbitrary Cypher queries.
  - Pattern 3, Graph-First — it does not begin by selecting graph entities before text retrieval.
  - Pattern 2, Parallel Hybrid — vector retrieval and graph search are not yet independent parallel branches fused afterward.

  It has partial pieces of the other two:

  - Pattern 5, Adaptive Router Agent: query routing exists for visual, literature, identifier, and standard text/graph questions.

  - Pattern 6, Agentic GraphRAG: tool routing exists for Axial, OOI M2M, PI Portal, EarthScope, Nereus, QA/QC, etc., but should
    run only when the question needs current data, analysis, plotting, or deeper retrieval.

  The best target architecture is:

  Adaptive Router
  ├─ normal knowledge question → Vector-First Hybrid GraphRAG
  ├─ figure question → visual retrieval + graph
  ├─ literature question → scientific index + full-text evidence + graph
  ├─ identifier question → keyword/metadata + graph
  └─ current-data/action question → GraphRAG evidence → agentic tool execution
