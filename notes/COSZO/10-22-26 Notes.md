## SCPR Data Meeting 

 **Attendees:** Maleen, Dana, William, Mika

Getting SCPR data into EarthScope
---
### Current Data State

- Existing SCPR data in PI Web is stored as `.dat` files containing **voltage values**, not physical/engineering values.
- A **Ceres instance** has been running and connected to SCPR since approximately **August**, generating NetCDF files for new incoming data.
- **Three data streams** exist from the instrument:
    - Pressure Sensor 1 — outputs pressure, pressure period, temperature period
    - Pressure Sensor 2 — same parameters
    - Engineering Channels — piston heights (in volts), valve states, calibration event logs

---
### Technical Challenges

- **Temperature conversion** requires Paros gauge calibration parameters (unique per sensor), which Glenn has not yet provided.
- All other conversions use simple constant-based equations.
- Historical `.dat` data has **not** been converted; only new data (since ~August) exists in NetCDF.
- NetCDF files are currently on a **test VM**, not in a permanent location.

---
### Key Decisions & Reasoning

- **Send L1-level data to EarthScope** (converted to engineering units, not calibrated values).
    - Rationale: Calibrations can change retroactively, invalidating prior data; a Python calibration script will be provided separately on COSO GitHub.
- **Historical data**: Convert directly from `.dat` to MiniSEED — skip NetCDF middle step.
- **New data**: Pull sample NetCDF files for scripting reference.
- EarthScope hosting of calibration scripts is a **future goal**, not currently available.

William's core idea was to **skip unnecessary intermediate steps** and take the simplest, most direct path to getting data into EarthScope. Here are the key points William raised:

- **Avoid mass NetCDF conversion of historical data:** William questioned the need to convert 7–10 years of old `.dat` files into NetCDF, arguing it is not the challenging part of the workflow.
    
    - William noted that reading a different file format is only "10–20 lines of code different," so the format conversion itself is trivial.
- **Focus on the hard part — getting data into EarthScope:** William emphasized that the real challenge is the EarthScope submission pipeline itself (they are "not incredibly responsive" and there are "all kinds of issues"), not the internal format conversions.
    
- **Raw/L1 data, not calibrated values:** William supported sending unconverted (L1-level) data to EarthScope, with a separate Python script for calibration.
    
    - Rationale: Calibrations can change retroactively, affecting previously stored data, so raw data should be archived and calibration applied separately.
- **Python calibration script on COSO GitHub:** William suggested that Glenn and Yoichiro collaborate on a Python script hosted on the COSO GitHub to allow users to convert raw data to calibrated values.
    
- **Practical next step:** William suggested demonstrating the end-to-end pipeline (PI NAS → EarthScope) as the priority, and then being better prepared when new COSO instrument data starts coming in.
    

In summary, William's position was: take the easiest, most direct conversion path for historical data, focus engineering effort on the EarthScope submission pipeline, and keep calibration as a separate, user-applied step.
