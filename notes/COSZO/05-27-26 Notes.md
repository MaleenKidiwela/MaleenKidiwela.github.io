**Meeting Overview**  
The team met to finalize the COSZO channel list for submitting data to EarthScope, focusing on naming conventions for GSSM, SCPR, and current meter instruments.

**Key Decisions – Channel Naming**

- GSSM remaining channels (max app memory, system available memory, UART power state) assigned as LE-type engineering codes (LE7, LE8, LE9 or descriptive variants)
- SCPR pressure/temperature period values treated as L0/engineering data, using LE-type codes (LE1, LE2, etc.), differentiated by location codes
- Tilt channels named LAX and LAY for X/Y axes
- Internal barometric pressure: LDI; internal temperature: LKR
- Current meter water velocity (ENU): MOE, MON, MOZ
- Amplitude data: MY1, MY2, MY3; correlation data: ME1, ME2, ME3
- Heading/pitch/roll: LEH, LEP, LER
- Speed of sound: LW (using wind code W as a proxy for meters/second)
- Location codes are flexible (numbers or capital letters, up to 2 characters)

Based on the meeting discussion, here is how backfill data gaps should be handled:
- **Sending backfill data:** As long as backfill data is sent through the ring server, EarthScope will capture it all.
- **Gap detection:** If a gap is noticed in the EarthScope archive, reach out to Tim Ronan, who can investigate why the gap occurred.
- **Gap resolution:** If a local copy of the data exists on your side, EarthScope can backfill those gaps — though Tim Ronan noted that gaps are fairly rare.
- **Don't delay sending data:** Even before metadata is archived, time series data should still be sent promptly, as it will be stored in EarthScope (just not publicly available until metadata is ready).
- **Navy-screened / redacted data:** For data going through the Navy data diversion switch, EarthScope will capture all the redacted/backfill data as well.
- **Multiple ring servers:** Data from separate ring servers (e.g., the shore station seedlink server and the local ring server) can all be sent to EarthScope without issues.

Key points Dana wanted communicated:
- The COSZO data flow will not follow the same path as the Axial SCPR data
- For COSZO, the plan is to produce **NetCDF files** first, then convert to MiniSeed
- The raw data formats are completely different between the two systems
- I was also encouraged to ask William whether he still wants to pursue that approach, given that any code written for the Axial SCPR could potentially be repurposed for future ones

Based on the meeting discussion, the Axial SCPR raw data push will include only the **non-calculated (raw) values**, as there is no processing pipeline on the RCA side to generate calculated values for those units. Specifically:

- **Pressure period values** (P1 and P2 press period) — treated as engineering/L0 data, assigned LE-type channel codes (e.g., LE1, LE2), differentiated by location codes
- **Temperature period values** — the instrument only outputs the temperature period (not actual temperature), so these raw frequency/period values are included as engineering data (e.g., LET-type)
- **Raw piston heights** — assigned LE3 with different location codes for each sensor
- **Raw barometric pressure** — voltage-level output, treated as engineering data (LE-type)
- **P1 and P2 calculated pressures** — these are output directly by the instrument after on-board calibration, so they are included (location codes 40/41 range)

The **calculated temperature values** (P1 temp, P2 temp) and other derived values shown in gray on the channel list are **not** being calculated for the Axial systems — Scripps is handling their own calculated values via FTP separately.

The team agreed to start by pushing what is currently available (raw values) and add calculated channels later as the pipeline matures.
