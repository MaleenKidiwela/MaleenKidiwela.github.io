**The Data Pipeline: PI NAS to EarthScope**

The primary objective is to develop a protocol to move data from the **PI NAS** (Network Attached Storage) to **EarthScope**. Currently, the team views data sitting solely in the PI NAS as "functionally useless" and wants to ensure all project data, including that from "COSZO," eventually ends up in EarthScope.

- **Test Case:** The team plans to use data from Scripps **SCPRs** (Self-Contained Pressure Recorders) as a test case to develop these data streams.
- **Frequency:** Data transfer is intended to be **daily** rather than real-time.
- **Raw vs. Calibrated Data:** The strategy for EarthScope is to ingest **raw data** rather than derived products. The modern approach is for users to request data which is then processed into useful products "on the fly" in the cloud.

**Software and Technical Processing**

Because EarthScope will primarily host raw data, the project requires local tools to make that data useful for scientists.

- **Python Packages:** There is a plan to create a Python-based package—modeled after **OBSpy**—that allows users to import functions for pulling, cleaning, and applying calibrations to the data.
- **Clock and Timing Corrections:** A significant portion of the data management effort involves correcting **timing jumps** and data gaps. The team emphasizes the need for scripts that can handle clock jumps by setting boundaries rather than averaging data across the jump.
- **Derived Products:** Beyond pressure data, the team is looking at products for **HYS4** and other short-period data requiring clock corrections.

**Infrastructure: GitHub and Website Migration**

The meeting participants expressed dissatisfaction with the current "COSZO" website, noting it "absolutely sucks" and remains "under construction".

- **WordPress Migration:** The plan is to migrate the project's public face to a **WordPress** site to meet disability requirements and simplify maintenance.
- **GitHub Integration:** GitHub is identified as the central hub for hosting software, Python scripts, and technical instrument documentation, such as **README files** explaining timing fixes.
- **Collaborative Benefits:** Using GitHub allows for collaborative development where multiple researchers can branch or fork repositories, though there were noted concerns regarding GitHub’s **100MB file size limit** and the complexities of managing private versus public repositories.
